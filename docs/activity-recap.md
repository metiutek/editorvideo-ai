# Activity recap

The **recap** tab builds an ordinary editable project from ordered activity groups and your own music. It reuses media-bin imports and resumable uploads, `story.segment_bounds` (also used by `plan_edit`), cached frame statistics, music beats/energy profiles, the configured vision-model adapter, `Store.add_clips`, undo/redo, project JSON, keyframes and the existing exporter. It does not render a flattened movie into the timeline.

## Use

1. Create and save an **empty** project. Existing edits are never overwritten.
2. Open **recap**, import each activity folder, or select a parent containing several activity folders. Repeat to add more folders. Alternatively import by reference in **media** and choose **Use folders from media bin**. Nested folders are separate activity groups; check the displayed groups before generating.
3. Drag activities into the required order (the up/down buttons are keyboard-accessible alternatives). Remove unwanted groups. Set optional target seconds or relative weights. Every included activity needs at least 0.5 seconds of usable footage.
4. Upload your background music or select an imported audio file. Choose duration, aspect ratio and pace. The music must cover the requested duration; it is not silently looped.
5. Configure a vision-capable model in **assistant → model settings**, review the analysis disclosure, enable consent and click **Generate recap video**. Cancel stops at the next analysis boundary; an in-flight model request may take up to its 240-second timeout. Nothing is added to the timeline after cancellation.
6. The resulting video clips and separate music track appear on the timeline as one undoable operation. Select a clip to see its original activity, source path and source range in **properties**. Move, trim, replace media, add text/stickers/graphics/transitions and animate parameters with the existing keyframe controls. Source audio is retained on the video clips, muted by default, and can be unmuted.
7. Save with the usual controls; reopen the JSON project to continue editing. Use the usual **export** dialog to render. Keep the referenced media files alongside the project.

## Model configuration, data and cost

No new service or dependency is introduced. The existing `llm.chiedi_con_immagini` adapter supports the selected Anthropic model (`.[chat]` required), an OpenAI-compatible vision endpoint (including a locally hosted compatible model), or Claude Code with image-reading support. Select a model that can actually interpret images and return JSON. Text-only models are not a supported fallback. Configuration/keys stay in the existing `~/.vedit/llm.json` or provider environment variables and never enter project JSON.

After explicit consent, the adapter receives JPEG contact sheets: three chronological 256×144 frames per candidate shot, up to eight rows per request, plus the scoring prompt. Full videos, original audio, music and source file names are not sent in the API payload. Claude Code receives the temporary sheet's local path so it can read it; its model may use a remote service. Source images can contain identifiable people or text. A remote provider may charge per request/image/token; check its current pricing. There is no fixed price estimate or automatic charge limit. The request count scales with the number of candidate shots (roughly one call per eight shots on an uncached file), and retrying a partially failed file may repeat that file's requests.

Local statistics, scene boundaries and music analysis use their existing caches. Successful visual analysis is cached per source path/size/nanosecond mtime, adapter type/model/endpoint and analysis version. Changing activity weights, order, duration or pace reuses those ratings. Failures are not cached; retry reuses other successfully analyzed files. Changing a file or model invalidates its visual cache. The UI's unfinished form/job ID lives only in browser session storage; the generated clips, source provenance and animations live in the project itself. The existing cache location is controlled with `VEDIT_CACHE`.

## Selection and timing

Candidates cover the entire file using the existing scene-aware segmentation, not random timestamps or only file beginnings. The model rates visible content, clarity, camera stability and representativeness. Local brightness statistics exclude all-black/all-white windows. Perceptual difference hashes reject near-identical candidate frames within each activity, and repeated semantic descriptions are penalized while sequencing. These are sampled visual assessments: three frames cannot prove that every intervening frame is sharp/stable, and perceptual hashes can reject different shots with similar compositions.

Each activity receives an integer-frame budget. Explicit targets are fixed to the nearest frame; remaining time is distributed by weight with a minimum of 0.5 seconds and capped by distinct usable footage. Infeasible targets or missing usable material fail with actionable errors. Activity boundaries preserve these budgets, even when they do not land on a beat. Within each group, cut lengths follow the selected pace, measured music energy, detected beats and strong energy-profile changes. A beat is preferred when feasible; exact total/target durations and source limits take precedence. Music structure is estimated from energy changes, not a semantic verse/chorus model.

`Store.apply_recap` independently validates activity membership/order, contiguous timeline positions, source bounds, non-overlapping uses of a source path, total duration and music coverage before a single atomic batch. A source video cannot be assigned to multiple activities. Generated clips carry immutable original selection provenance (`activity`, activity name, source path, original in/out, visual subject); their current editable range remains in the existing `in`/`duration` fields. Manual edits after generation are deliberately unrestricted. If the project changes while analysis is running, the job refuses to apply stale results and asks for a retry using the cache.

## Validation and limits

`tests/test_recap.py` covers ordered groups, allocation/capacity failures, original source bounds, duplicate intervals, cancellation/model failures/stale-project protection, consent, cache invalidation/model changes, project persistence, undo/redo and subsequent trimming/moving/keyframing. Its `slow` integration test creates **two activity folders with two videos each and one music file**, runs real scene/frame/music analysis, builds the timeline, modifies clips/animation, saves/reopens and renders a real MP4. Only the paid model's ratings are simulated. `frontend/smoke.mjs` exercises the recap form, consent gate, generation payload and cancellation, alongside the existing editing UI checks.

Validation on this implementation: **19 recap tests passed**, including the real-export integration test. The full `pytest -m "not slow"` run completed with **926 passed, 1 skipped, 1 failed, 214 deselected** (the three final preflight/timing tests were added afterwards and passed in the targeted run). The sole failure was `tests/test_render_pezzi.py::test_scale2ref_porta_alla_misura_del_riferimento`, where FFmpeg did not produce the expected PNG. The same test failed identically against the untouched base commit `ac1b8532f73c3c7fde4596abba0ba8d834b774aa`. Frontend build and all five existing test scripts passed; the added checks cover actual activity dragging and upload-cache separation for identically named videos in different activities. The full suite required local socket access outside the Windows sandbox for FastAPI's TestClient.

Verified on Windows with Python 3.12, Node 24 and FFmpeg 7.1 from a test-only `imageio-ffmpeg==0.6.0` installation (`VEDIT_FFMPEG` override); ffprobe 9 was used for probing. The repository already documents Windows, macOS and Linux support; this change adds no OS-specific dependency. macOS/Linux execution, a real configured vision-provider response, human evaluation of real-event footage, and a full manual browser editing session have **not** been verified in this environment. The system FFmpeg 9 rejects the existing exporter's `-filter_complex_script`; use a compatible FFmpeg build until the upstream exporter is updated. This PR does not replace that exporter.

Jobs are in memory and do not survive server restarts; completed source analyses remain cached. Cancellation is cooperative and does not abort an already-issued remote request or refund it. Visual caching is per completed file, not per individual model batch. No automatic transitions or graphics are applied; those remain the editor's existing manual tools. The JSON project references source paths rather than bundling media. Visual model ratings are real integration code, but the quality of model choices remains unverified until a configured provider is exercised on real footage.
